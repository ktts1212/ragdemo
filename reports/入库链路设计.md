# 入库链路设计（上传 → 异步入库 → 落库）

> 代码：`controller/DocumentController` · `service/serviceImpl/{DocumentServiceImpl, IngestionServiceImpl, KafkaProducerService, KafkaConsumerService, MinioServiceImpl}` · `rag/ingest/*` · `persistence/AcademicChunkPersistenceMapper` · `document/pipeline/CanonicalDocumentPipeline` · `workflow/**`（图链路）
> 表：`documents` / `ingestion_tasks` / `document_chunks`（见 `数据库表结构说明.md`）· 对象存储：MinIO（决策 D2 key）
> 建表：**`sql/init.sql`（单文件，已合并 V2–V10）**
> 注意：本报告描述**旧链路（默认）**与**图链路（可开关）**两种执行方式；生产默认 `rag.workflow.ingestion.enabled=false`（旧链路）。

---

## 一、总览

```text
【同步】POST /api/documents/upload  (file, knowledgeBaseId?=1, parseMode?)
  1 validateFile            .pdf/.docx/.txt/.md
  2 checkKnowledgeBaseExists
  3 extractFileExt / generateStoredFileName(uuid) / calculateSha256(流式)
  4 ★解析模式三级决策 → parseMode（AUTO/ACADEMIC/GENERIC）
  5 ★先 INSERT documents（拿 id；storage_path 先空串）
      └ documents.parse_mode = 决策结果, version = 1
  6 ★按 parseMode 算 artifact key → MinIO 上传源文件
      ├ ACADEMIC: documents/{id}/versions/{v}/source/original{ext}
      └ GENERIC : knowledge-base/{kbId}/{yyyyMMdd}/{uuid}{ext}     ← 保持原样（零回归）
  7 updateStoragePath 回填
  8 INSERT ingestion_tasks(status=pending)
  9 Kafka send  rag-document-ingestion  {documentId, knowledgeBaseId, taskId}
  10 返回 KnowledgeDocumentDto

【异步】KafkaConsumerService.consume(msg) 或 恢复调度器扫描
  → IngestionServiceImpl.ingest(documentId, taskId)          ← 统一入口
  1 markTaskRunning(taskId)（图链路走租约抢占，见 §一.1）
  2 selectById(documentId)；为空 → task failed
  3 status == "indexed" → 幂等短路，task success（图链路：先做三态对账，再决定是否补 finalize）
  4 ★分流 ParseMode.from(documents.parse_mode)
      ├ ACADEMIC → 旧链路：AcademicIngestionService.ingest(...)
      │             图链路：WorkflowExecutionCoordinator → 图（prepare→parseArtifact→chunk→embedBatch→persist→finalize）
      └ 其它     → ingestGeneric(document, taskId)（永不进图）
  5 catch(Exception) → documents.status=failed + task failed（**不静默回退**）
```

### 一.1 两条执行路径（关键差异）

| 维度 | 旧链路（默认） | 图链路（`rag.workflow.ingestion.enabled=true`） |
|---|---|---|
| 代码入口 | `AcademicIngestionService`（10 步顺序调用） | `WorkflowExecutionCoordinator` → LangGraph4j 图 |
| 阶段边界 | 方法内顺序执行，无检查点 | 每个节点执行后写 1 条 Checkpoint（`checkpoint-enabled=true`） |
| 崩溃恢复 | 无（进程死则任务停在 running） | 对账 + 租约过期接管 + `resume()`（见 `崩溃恢复rep/`） |
| 执行权 | 无锁 | DB CAS 租约 + `fencing_token`；写入校验 owner+token |
| 自动恢复 | 无 | `recovery-enabled=true` 时调度器周期扫描（间隔 30s / 批量 10 / 并发 2） |
| 产物复用 | 无 | marker-raw / canonical(+meta) / chunks / embeddings 批次（按 fingerprint） |
| 三态一致性 | 由 `indexed` 短路保证 | `documents.status` / `ingestion_tasks.status` / Graph END 三者对账 |

> 两条链路共用：`ChunkPersistenceService.replaceChunks`（唯一 `@Transactional` 写入）、`IngestionStatusUpdater`、MinIO artifact key 规则。

## 二、上传阶段的关键设计

### 2.1 parseMode 三级决策（决策 D1）

```text
优先级：① 上传参数 > ② 配置默认 > ③ 扩展名/MIME 自动
  requested=ACADEMIC            → ACADEMIC
  requested=null/AUTO + 配置=AUTO + .pdf → ACADEMIC   （AUTO：PDF → 学术链路）
  requested=null/AUTO + 配置=AUTO + .md  → GENERIC
```

组件：`rag/ingest/ParseMode`（枚举 AUTO/ACADEMIC/GENERIC + 宽松 `from(String)`）、`ParseModeResolver`。
**决策结果落库**到 `documents.parse_mode` —— 异步 worker 据此分流 ⇒ 可审计、可重试、可人工纠正。

### 2.2 为什么"先 INSERT 再上传 MinIO"

因为 ACADEMIC 的 MinIO key 含 `documentId`（决策 D2），而 id 由 DB 自增产生：

```text
INSERT documents(storage_path = '')  → 拿到 id
  → 算 key → MinIO 上传 → UPDATE storage_path
```

代价：`storage_path` 有"空串"中间态（列 NOT NULL，用空串而非 NULL 规避）。上传失败 → 事务回滚（DB 无记录，MinIO 可能残留 → 见缺口 #7）。

### 2.3 文件校验与指纹

- 允许扩展名：`.pdf` / `.docx` / `.txt` / `.md`
- `checksum` = **流式 SHA-256**（`DigestInputStream`，不整文件读入内存）
- `checksum` 在 ACADEMIC 链路里被用作**领域 documentId**（见 §4.2）

## 四、ACADEMIC 链路（`AcademicIngestionService`）

```text
1 状态 parsing(20%)
2 从 MinIO 下载源文件（readAllBytes 到内存）
3 CanonicalDocumentPipeline.process(domainDocumentId, pdfBytes, fileName)
     = Marker API → MarkerDocumentParser → ReadingOrderRepair → PaperCleaner（→ Canonical）
4 ★hard-invalid 检查：result.valid()==false → 抛 ACADEMIC_INVALID_CANONICAL（**不写 indexed**）
     warning-only（valid==true + warnings）→ 允许入库，仅 log.warn
5 artifact 落盘（先存，便于离线重跑）：marker-raw.json → canonical.json
6 状态 chunking(45%)：SectionAwareChunker.chunk(canonical) → chunks；空 → 抛 ACADEMIC_NO_CHUNKS
     artifact 落盘：chunks.json（manifest：chunkId/chunkType/order/tokenCount/sectionPath/pages/sourceBlockIds/contentHash）
7 状态 embedding(70%)：EmbeddingGateway.embedDocuments(chunks 的 embeddingText)
     └ 分批(32) + 指数退避有限重试（仅超时/5xx；维度不一致/4xx 不重试）
     └ ★在 DB 事务【外】执行（skill §14）
8 AcademicChunkPersistenceMapper.toInsertParam(chunk, dbDocumentId, kbId, vector)
9 ChunkPersistenceService.replaceChunks(documentId, params)   ← 唯一 @Transactional
     deleteByDocumentId → 逐条 insert → updateChunkCount → status=indexed
10 markTaskSuccess(taskId)
```

### 4.1 失败语义（错误码前缀）

| 错误码 | 触发 |
|---|---|
| `ACADEMIC_DOWNLOAD_FAILED` | MinIO 下载异常 |
| `ACADEMIC_MISSING_CHECKSUM` | 无 checksum（无法得到领域 id） |
| `ACADEMIC_INVALID_CANONICAL` | canonical hard-invalid（附 errors 列表） |
| `ACADEMIC_NO_CHUNKS` | 分块结果为空 |
| `ACADEMIC_ARTIFACT_WRITE_FAILED` | artifact 序列化/上传失败 |

任一步抛出 → `documents.status=failed` + `ingestion_tasks=failed` + `error_message` 记录；**绝不静默回退为 GENERIC 再标 indexed**。

### 4.2 两个关键设计

**① 领域 documentId = 文件 SHA-256（而非 DB 自增 id）**
- 依据 skill §5.1：DB surrogate key 不进领域对象
- 内容寻址 ⇒ `chunkKey = {sha256}:{scopeId}:{index}` 在**重传相同内容时保持稳定** ⇒ 幂等 + 可 diff
- 实测：`9670ffc08b26…eff1:__abstract__:0`

**② embedding 由 `embeddingText` 现算（不是 `content`）**
- `AcademicChunkPersistenceMapper` 提供接收 `EmbeddingGateway` 的重载，从**契约层**保证 embedding 输入是 `embeddingText`
- `content` 与 `embedding_text` **两者都入库** ⇒ 可复现 / debug / content-vs-embeddingText 消融

## 五、GENERIC 链路（原有逻辑，行为不变）

```text
parsing(20%) → MinIO 下载 → DocumentParseService.parse（LangChain4j pdfbox/poi/tika）
→ chunking(45%) → TextSplitterService.split（字符递归 800/120）→ updateChunkCount
→ embedding(70%) → EmbeddingModel.embedAll
→ deleteByDocumentId → 逐条 insert（**学术列全为 null**）→ status=indexed → markTaskSuccess
```

与 ACADEMIC 的差异：

| 维度 | GENERIC | ACADEMIC |
|---|---|---|
| 解析器 | LangChain4j（pdfbox/poi/tika） | Marker → Parser → Repair → Cleaner |
| 分块 | 字符递归 800/120 | SectionAwareChunker（token 预算） |
| embedding 来源 | `content` | **`embeddingText`**（带 Document/Section 前缀） |
| 学术列 | 全 null | chunk_key/chunk_type/section_*/embedding_text/content_hash/end_page |
| 源文件 key | `knowledge-base/{kbId}/{date}/{uuid}{ext}` | `documents/{id}/versions/{v}/source/original{ext}` |
| artifact | 无 | marker-raw / canonical / chunks.json |
| 事务 | **无 `@Transactional`**（逐条 insert） | `ChunkPersistenceService.replaceChunks` @Transactional |

## 六、状态机与幂等

```text
documents.status : uploaded → parsing → chunking → embedding → indexed
                        └────── 任一步失败 → failed（终态）

ingestion_tasks.status : pending → running → success | failed
                          ├─ retry_wait（瞬时错误 + 退避到期，仅图链路）
                          └─ waiting   （等待人工确认，仅图链路）
```

幂等保障：
1. `documents.status == "indexed"` → `ingest` 直接短路（重复投递无副作用）；图链路在此基础上先做三态对账（Graph 未 END 仍会补 finalize）
2. `deleteByDocumentId` + 重插（重试/重跑安全）
3. `UNIQUE(document_id, chunk_index)` — 结构性兜底
4. `uk_document_chunks_chunk_key` — chunkKey 唯一（内容寻址 ⇒ 重传内容相同时 key 相同）
5. MinIO artifact 按 version 覆盖写（同 version 重跑 = 覆盖，天然幂等）
6. 图链路：DB CAS 租约 + `fencing_token`（旧 Worker 迟到提交被拒） + 同文档单活跃任务部分唯一索引

## 九、已知缺口（11 项）

| # | 缺口 | 影响 |
|---|---|---|
| 1 | **批量 insert 未做** | `replaceChunks` 逐条 `insertChunkWithEmbedding`；126 条 = 126 次往返（skill §14 要求 batch） |
| 2 | **`batchUpload` 仍返回 null** | `DocumentServiceImpl.batchUpload` 未实现 |
| 3 | **`version` 无递增入口** | 字段与 key 已就绪，但没有"重跑解析"的 API/入口 ⇒ `version` 恒为 1 |
| 4 | **消费重试 / 死信：已实现但默认关闭** | `KafkaReliabilityConfig`（`DefaultErrorHandler` 2 次重试 + `DeadLetterPublishingRecoverer` + DLT topic）需 `rag.kafka.reliability.enabled=true`；真实 broker 上的 ack/DLT 验收未通过，故**默认关闭**。当前保底是恢复调度器扫描 `pending` |
| 5 | **Kafka 消息不自包含** | 不含 parseMode（从 DB 读）⇒ 消息无法脱离 DB 单独重放 |
| 6 | **旧链路仍无并发控制（图链路已解决）** | 旧链路同文档并发会互相 delete/insert（靠 UNIQUE 兜底）；图链路用 DB CAS 租约 + `fencing_token` + `uk_ingestion_tasks_active_document` 保证单活跃任务 |
| 7 | **MinIO 残留** | 上传/入库失败时已写入的对象不清理（`MinioService.delete` 是空实现） |
| 8 | **`ingestion_tasks.current_step` 未写入** | 列就绪、代码未用 ⇒ 无法看到"卡在哪一步" |
| 9 | **`ingestion_tasks.progress` 更新点缺失** | 文档 progress 有 20/45/70/100，但 task 的 progress 只在 start/finish 变更（待确认） |
| 10 | **无文件大小/页数上限** | 仅靠 Spring multipart 50MB；无 PDF 页数/解析超时上限 |
| 11 | **源文件会整份读入内存** | `AcademicIngestionService` 用 `readAllBytes()` ⇒ 大 PDF（数百 MB）有 OOM 风险 |

## 十、一句话总结

```text
上传（同步）：校验 → SHA-256 → 三级决策 parseMode → 先插 documents 取 id
            → 按 parseMode 算 MinIO key（ACADEMIC 版本化 / GENERIC 旧路径）→ 建 task → 发 Kafka
入库（异步）：Kafka → ingest 分流（ACADEMIC / GENERIC）
  ACADEMIC：下载 → Marker→Canonical → hard-invalid 拦截 → 存 marker-raw/canonical/chunks
            → Chunker → 分批 embedding（事务外）→ 映射 → 唯一事务写入（delete→insert→indexed）
  GENERIC ：LangChain4j 解析 → 字符分块 → embedAll → 逐条写入
失败语义：一律 failed，绝不静默回退；幂等靠 indexed 短路 + delete 重插 + 两个唯一约束
缺口：无批量 insert / 图链路默认关闭 / version 无递加入口 / MinIO 不清理 / 大文件全量入内存
```
