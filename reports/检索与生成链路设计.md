# 检索与生成链路设计

> 代码：`controller/ChatController` · `service/serviceImpl/ChatServiceImpl` · `retrieval/DocumentRetrievalService` · `mapper/DocumentChunkMapper(.xml)`
> Prompt：`resources/prompt/{system,user}-prompt.txt` · 依赖：`config/{EmbeddingConfig,ChatModelFactory,RagProperties}`
> 上游记忆：L2（会话上下文）+ L3（跨会话长期记忆，见 `记忆系统设计.md`）· 数据：`document_chunks`（见 `数据库表结构说明.md`）

---

## 一、链路总览

```text
POST /api/chat   { question, topK?, knowledgeBaseId?, minScore?, model?, conversationId? }
   │
   ▼ ChatController  →  ChatServiceImpl.chat()
   │
   ├─ 1. validateRequest()            question 非空 / topK>0 / minScore∈[0,1]
   ├─ 2. 默认值                        kbId=1 · topK=5 · minScore=0.3
   │
   ├─ 3. 记忆层（详见记忆系统报告）
   │       resolveConversationId → loadRecentMessages(16) → getSummary → getSessionState
   │       → rewriteQuestion(...)   ← 得到 questionForSearch（受 rag.query-rewrite.enabled 控制）
   │
   ├─ 4. DocumentRetrievalService.retrieve(RetrievalRequest)
   │       ├ EmbeddingModel.embed(questionForSearch)        → float[1024]
   │       ├ toPgVectorString(float[])                      → "[0.12,-0.34,...]"
   │       └ DocumentChunkMapper.searchSimilarChunks(kbId, vec, topK)   ← pgvector cos topK
   ├─ 5. Java 侧 filter(score >= minScore)
   ├─ 6. 空则短路：直接返回「根据当前知识库资料无法确定。」+ 空 sources（**不调 LLM**，L3 也不替代此判断）
   ├─ 7. buildContext()  → 【资料1】…【资料N】
   ├─ 8. ★L3 注入：MemoryL3ContextService.load(question)（路由命中才查）
   │       → 追加在【结构化状态】之后，作为"引用数据"块（不是指令，不替代论文引用）
   ├─ 9. 组装 messages：SystemMessage(规则) → 历史消息(16 条) → UserMessage(摘要+状态+L3+资料+问题)
   ├─ 10. ChatModelFactory.getModel(model).chat(...)      → answer
   ├─ 11. 组装 SourceReference[]（docName/chunkIndex/score/preview/content/page）
   ├─ 12. ★原子提交：L3TurnCommitService.commitTurnAndEnqueue（消息保存 + L3 Outbox 同事务）
   │       失败 → memoryDegraded=true / memoryWarning=CONVERSATION_PERSIST_FAILED
   ├─ 13. 派生记忆：updateSessionState +（必要时）updateSummary
   │       失败 → memoryDegraded=true / memoryWarning=MEMORY_DERIVED_UPDATE_FAILED
   └─ 14. 返回 { answer, sources, conversationId, memoryDegraded, memoryWarning }
```

> L3 只增加**一次向量化 + 若干数据库检索**，不增加对话模型调用；一轮问答的对话模型调用上限仍是
> **4 次**（改写 / 回答 / 状态 / 摘要）。

## 二、组件与职责

| 组件 | 职责 | 关键点 |
|---|---|---|
| `ChatController` | `POST /api/chat` | 只有转发，无业务；异常由 `GlobalExceptionHandler` 兜底 |
| `ChatServiceImpl` | 检索 + 生成编排（14 步） | 唯一业务编排点 |
| `DocumentRetrievalService` | 检索能力封装 | 与 Agent 工具复用同一实现；SQL 仍是 `searchSimilarChunks` |
| `MemoryL3ContextService` | L3 读取门面 | Router → Retriever → ContextBuilder；失败只降级（空块） |
| `EmbeddingModel` bean（`EmbeddingConfig`） | 问题向量化 | LangChain4j `OpenAiEmbeddingModel`：`baseUrl=ollama/v1`、`model=bge-m3:latest`、`timeout=2min`。**与入库侧共用同一个 bean** |
| `DocumentChunkMapper.searchSimilarChunks` | pgvector 相似度检索 | SQL 在 `mapper/DocumentChunkMapper.xml` |
| `ChatModelFactory` | LLM 选择 | 按 `rag.models.<key>` 建 `OpenAiChatModel`，`ConcurrentHashMap` 缓存；key 缺省取 `rag.default-model`（deepseek） |
| `ConversationMemoryService` | 记忆（见独立报告） | — |
| `RagProperties.retrieval` | `top-k=5` / `min-score=0.3` | 请求级可覆盖 |

## 三、检索 SQL（唯一的检索入口）

```sql
SELECT dc.id AS chunkId, dc.document_id AS documentId, d.file_name AS documentName,
       dc.page_number AS page, dc.chunk_index AS chunkIndex, dc.content AS content,
       1 - (dc.embedding <=> CAST(#{questionEmbedding} AS vector)) AS score
FROM document_chunks dc
JOIN documents d ON dc.document_id = d.id
WHERE dc.knowledge_base_id = #{knowledgeBaseId}
  AND d.status = 'indexed'                       -- 未完成入库的文档不参与问答
ORDER BY dc.embedding <=> CAST(#{questionEmbedding} AS vector)
LIMIT #{topK}
```

要点：
- `<=>` = pgvector **余弦距离**；`1 - 距离` = 余弦相似度（0~1）
- 过滤条件只有 **`knowledge_base_id` + `documents.status='indexed'`**
- **没有** `chunk_type` / `section_path` 过滤，**没有** ANN 参数（`ivfflat lists=100` 是建索引时的静态配置）
- 无 `HAVING`/去重/多路召回

## 四、Prompt 契约

### system-prompt.txt（8 条硬约束）
```text
1 只能根据【知识库检索资料】回答    2 不用资料外知识补充
3 资料没有 → 回「根据当前知识库资料无法确定。」
4 不编造文献/页码/实验结果/数据集/指标/结论
5 尽量标注依据（「根据资料1和资料2」）  6 资料冲突要明确说明
7 中文、简洁清晰                    8 有多轮历史时结合上下文理解意图
```

### user-prompt.txt（模板）
```text
{summary}{sessionState}【知识库检索资料】
{context}

【用户原始问题】
{question}

【回答要求】
1 回答【用户原始问题】，不要回答其他内容   2 必须基于【知识库检索资料】
3 资料不足 → 回「无法确定」              4 使用了资料要标注来源（「根据资料1」）
5 中文、简洁清晰
6 会话摘要和结构化状态仅用于理解上下文指代，不作为事实依据   ← 防幻觉关键条款
```

### 上下文块 `buildContext` 的格式
```text
【资料1】
文档名称：xxx.pdf
页码：3                      ← page 为 null 时整行省略
相似度分数：0.86
内容：
...chunk 原文（= document_chunks.content，纯净文本，不含 Section 前缀）...
```

> 注意：**检索用 `embedding`（其来源是带 `Document/Section` 前缀的 `embeddingText`），而喂给 LLM 的是 `content`（无前缀）** —— 有意分离：向量要章节语义，生成要干净原文。

## 五、输入 / 输出契约

```java
// 请求（除 question 外全部可空，空则取默认）
ChatRequestDto { question, topK, knowledgeBaseId, minScore, model, conversationId }

// 响应（后两个字段为记忆降级标记，旧客户端可忽略）
ChatResponseDto { answer, sources[], conversationId, memoryDegraded=false, memoryWarning }
SourceReference { docName, chunkIndex, score, preview(前 160 字), content(全量), page }
```

`docName` 取 `documents.file_name`（用户上传时的原始文件名）。

## 七、设计亮点（值得保留）

| # | 设计 | 价值 |
|---|---|---|
| 1 | **无命中直接短路，不调 LLM** | 省钱 + 从根本上防幻觉（而不是靠 prompt 求模型别编） |
| 2 | **system + user 双层约束，且明确"资料不足→无法确定"** | 拒答路径清晰 |
| 3 | **user-prompt 第 6 条**："摘要/状态仅用于理解指代，**不作为事实依据**" | 防止把记忆里的旧结论当事实引用 —— 很多实现会漏这一点 |
| 4 | **资料块带 docName + 页码 + 分数** | 让 LLM 能按「根据资料1」标注，**引用可追溯** |
| 5 | **检索用 embeddingText、生成用 content** | 向量取章节语义，生成取干净原文 |
| 6 | **入库侧与检索侧共用同一个 `EmbeddingModel` bean** | 避免"入库/查询用了不同模型或配置"这类静默质量杀手 |

## 八、已知缺口（8 项）

| # | 缺口 | 说明 / 影响 |
|---|---|---|
| 1 | **无 reranker** | README 把 rerank 列为"后续扩展"；目前只有 pgvector 单路 topK + minScore |
| 2 | **无 hybrid 检索（BM25/关键词）** | 纯向量，术语精确匹配（如罕见缩写、数字、公式符号）召回弱 |
| 3 | **两套 pgvector 字面量实现** | `DocumentRetrievalServiceImpl.toPgVectorString`（`float` 拼接）与 `VectorUtils.toPgVector`（`Double.toString`）输出不一致 → 应统一（当前检索走前者、入库走后者） |
| 4 | **`OpenAiClient` 仍为遗留类** | 仅自身定义与注释引用，未被任何 Bean 注入使用 ⇒ 实际是死代码（可删） |
| 5 | **新列的过滤能力未使用** | `chunk_type` / `section_path` / `section_level` 已在表里并建了索引，但检索 SQL 完全没用 → 无法"只在 Methods 里检索"、无法降权 REFERENCE |
| 6 | **REFERENCE 占比问题** | 历史实测目标论文 126 chunk 中 66 条（52%）是 REFERENCE，**全部平等参与检索**，易稀释 topK |
| 7 | **无 ANN 调参 / 无精确检索开关** | `ivfflat lists=100` 对当前规模偏大；小数据量下 ANN 召回可能劣于精确检索（QA 阶段应能切换） |
| 8 | **无 streaming、无缓存** | 一次返回；重复问题每次都重新 embedding + 检索 + 最多 4 次 LLM 调用 |
| 9 | **L3 只做"背景引用"** | L3 不替代论文来源引用：无 chunk 命中时仍直接拒答；L3 记忆不会进入 `sources` |
| 10 | **记忆失败对用户不透明** | L3 检索失败只写日志/Agent 警告；`/chat` 响应只有 `memoryDegraded`（针对持久化/派生记忆失败），不区分"L3 检索失败" |

## 九、一句话总结

```text
入口 POST /api/chat → 记忆层改写问题（可开关）→ bge-m3 embedding(1024) → pgvector 余弦 topK(5)
→ minScore(0.3) 过滤 → 无命中直接拒答（不调 LLM）→ buildContext【资料N】
→ L3 引用块（可选，注入在摘要/状态之后）→ System(8 条硬约束) + 历史16条 + User(摘要+状态+L3+资料+问题)
→ LLM → answer + sources → 原子提交(消息+Outbox) → 派生记忆 →（失败只标记 memoryDegraded）
亮点：拒答短路、记忆不作事实依据、引用可追溯、检索/生成文本分离、embedding 单一来源、L3 永不进 system
缺口：无 rerank / 无 hybrid / 新列过滤未用 / REFERENCE 未处理 / ANN 未调 / 两套向量字面量实现
```
