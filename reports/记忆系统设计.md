# 会话记忆系统设计

> 代码：`memory/`（`ConversationMemoryService` + `ConversationMemoryServiceImpl`）· `service/serviceImpl/ChatServiceImpl`
> 表：`chat_conversations` / `chat_messages` · Prompt：`resources/prompt/{summary,state,query-rewrite}-prompt.txt`

---

## 一、定位与目标

它是**短期记忆（会话级）**，但真正的目的**不是"让 LLM 记住聊天"**，而是：

> **把模糊的追问补全成独立问题，让向量检索能命中** —— 即服务于 **retrieval** 质量，而非仅生成连贯性。

因为检索是按"问题向量"做的：用户第二句说 *"它的参数量呢？"*，直接 embedding 检索必定失败。记忆层的作用就是在检索**之前**把这句改写成 *"PatchECG 模型的参数量是多少？"*。

接口注释里写的"一期：纯滑动窗口"已经过时 —— 实际实现是**三层**。

---

## 二、三层记忆结构

| 层 | 存储位置 | 内容 | 作用 | 更新时机 | 生成方式 |
|---|---|---|---|---|---|
| **① 滑动窗口** | `chat_messages` | 最近 **16 条**消息（`MAX_RECENT_MESSAGES=16` = **8 轮**问答） | 最精确的近期上下文，直接作为 chat 历史注入 LLM | 每轮 `saveTurn` 写 2 条（user + assistant） | 原样存原文 |
| **② 滚动摘要** | `chat_conversations.summary`（TEXT） | ≤300 字中文摘要（论文名 / 方法 / 数据集 / 指标 / 核心结论） | 窗口**外**的旧信息不丢 | 当 `countMessages > 16` 时，用**被挤出的最早一轮**与旧摘要合并 | **LLM 生成**（`summary-prompt.txt`） |
| **③ 结构化状态** | `chat_conversations.session_state`（JSONB） | 固定 schema：`{topic, method, dataset, metric, finding, task, keyTerms[]}` | 明确承载"**指代对象**"，供改写与注入使用 | **每一轮都更新**（从第 1 轮开始） | **LLM 生成 JSON**（`state-prompt.txt`） |

设计要点：
- **摘要**是**增量式**的：只喂"被挤出的那一轮问答"+ 旧摘要，而不是整个窗口 → 成本恒定
- **状态**是**逐轮**跟踪的（注释明确"从第一轮就开始跟踪，用于后续指代消解"），并给了兜底初值 JSON；prompt 要求"字段名固定、不能新增字段、不确定填 null 不编造"
- `keyTerms[]` 是**逃生口**：固定字段装不下的关键实体（对比方法、模块名…）放这里

## 三、一轮问答的完整时序（`ChatServiceImpl.chat`）

```text
1  参数校验；kbId / topK(5) / minScore(0.3) 填默认值
2.1 resolveConversationId   ← 前端传了则校验（不存在→降级新建，不报错）；没传→UUID 新建
2.2 loadRecentMessages(16)  ← 滑动窗口（DB 按时间倒序取出）
2.3 getSummary              ← 滚动摘要（可能 null）
2.4 getSessionState         ← 结构化状态（第 1 轮后就有值）
2.5 rewriteQuestion(summary, sessionState, recentMessages, question)   ← ① 第 1 次 LLM 调用
3   用【改写后的问题】做 embedding
4   → pgvector 向量
5   searchSimilarChunks(kbId, vec, topK)
6   minScore 过滤
7   无命中 → 直接回 "根据当前知识库资料无法确定。"（不调 LLM）
8   buildContext → 【资料1】【资料2】…
9   组装：SystemMessage(规则) → 历史消息(窗口 16 条，反转正序) → UserMessage(摘要+状态+资料+问题+要求)
10  LLM 生成答案                                                      ← ② 第 2 次 LLM 调用
11  组装 SourceReference（docName / chunkIndex / score / preview / content / page）
12  saveTurn(原始问题, 答案)          ← 落库 2 条
12.1 updateSessionState(原始问题, 答案)                              ← ③ 第 3 次 LLM 调用
13  若 countMessages > 16 → updateSummary(被挤出的最早一轮)           ← ④ 第 4 次 LLM 调用（条件触发）
```

**注意：一轮问答最多触发 4 次 LLM 调用**（改写 + 回答 + 状态 + 摘要）。

### 关键设计：改写只用于检索，LLM 用原问题

```java
String questionForSearch = ...rewriteQuestion(...);   // ← 只喂给 embedding
...
.replace("{question}", request.getQuestion());        // ← 传给 LLM 的仍是【原始问题】
```

好处：改写只影响**检索召回**，不改变用户实际提问的语义与语气，避免改写偏差污染生成。

## 四、组装顺序（注入 LLM 的上下文）

```text
SystemMessage        ← system-prompt.txt（规则约束）
历史消息 ×16         ← 窗口内，DB 倒序 → 反转正序
UserMessage          ← user-prompt.txt 模板替换：
                        {summary}       → 【会话摘要】…（无则整段省略）
                        {sessionState}  → 【结构化状态】…（无则整段省略）
                        {context}       → 【资料1】…【资料2】…
                        {question}      → 用户原始问题
```

即：**近期细节（窗口）在前，远期压缩（摘要/状态）在后，检索资料与问题在最后**。

## 五、会话生命周期与接口

| 能力 | 实现 | 接口 |
|---|---|---|
| 新建/复用会话 | `resolveConversationId`；`chat_conversations.id` 是 **UUID 字符串**（VARCHAR(64)，非自增） | 随 `/chat` 隐式创建 |
| 落库本轮问答 | `saveTurn` → 2 条 `chat_messages` + `touch` 会话 `updated_at` | 随 `/chat` |
| 会话列表 | `listConversations(limit)` 按 `updated_at` 倒序 | `GET /api/conversations?limit=50` |
| 删除/重命名/分页 | **无** | — |

## 六、实现细节

- 摘要 / 状态 / 改写**各是一次独立 LLM 调用**，模型统一走 `chatModelFactory.getModel(null)` → 取 `rag.default-model`（当前 deepseek）
- 三者的 prompt 都是**单条 UserMessage**（无 system message），模板在 `@PostConstruct` 时读入 `classpath:prompt/*.txt`
- 摘要入参的"被挤出轮次"取自 `recentMessages` 末尾 2 条（倒序数组的最后两个 = 时间上最早的一轮）
- 历史消息在 DB 侧 `ORDER BY created_at DESC LIMIT 16`，组装时在 Java 侧**反转**
- 会话不存在时**降级新建**而非报错（体验优先）

## 七、已知缺口（7 项，均已核实）

| # | 缺口 | 证据 / 影响 |
|---|---|---|
| 1 | **`rag.query-rewrite.enabled` 开关完全未被使用** | 全仓 grep `getQueryRewrite` 只命中 `RagProperties` 自身 → 改写**无条件执行**，配置是 dead config。想关掉改写目前**做不到** |
| 2 | **记忆层调用无 try/catch** | `saveTurn` / `updateSessionState` / `updateSummary` 直接裸调 → 记忆层故障（如 LLM 超时、JSON 非法）会让**整个 `/chat` 报错**，尽管答案已经生成。可用性被记忆层耦合 |
| 3 | **`session_state` 未做 JSON 校验** | LLM 若输出非法 JSON，`updateSessionState` 里 `session_state::jsonb` 写入失败即抛错（叠加 #2 → 整轮失败）。prompt 只做了"只输出 JSON"的软约束 |
| 4 | **`chat_messages.token_count` 从未写入** | 全仓 grep 只有实体字段，无写入点 → 该列恒为 NULL（与数据库说明报告中的记录一致） |
| 5 | 无长期记忆 / 跨会话记忆 | 摘要与状态都挂在**单个会话**上；换会话即失忆 |
| 6 | 无记忆淘汰 / 归档 | `chat_messages` 只增不减；摘要虽压缩但**原始消息永久保留**（无 TTL/清理） |
| 7 | 无法按会话清理 | 无删除接口；调试时只能手工清库 |

## 八、一句话总结

```text
三层：滑动窗口(16 条=8 轮) + 滚动摘要(≤300 字, 增量) + 结构化状态(固定 JSON, 逐轮)
用途：**为检索服务** —— Query Rewrite 把追问补成独立问题【只喂 embedding】，
      而传给 LLM 的仍是原始问题；摘要/状态则作为【压缩后的远期上下文】注入 UserMessage。
成本：一轮问答最多 4 次 LLM 调用（改写 / 回答 / 状态 / 摘要）。
缺口：开关未接线、无容错、状态未校验 JSON、token_count 未写、无跨会话记忆、无淘汰。
```
