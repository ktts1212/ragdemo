## 1. 决策点汇总（先定这些，才能动代码）

| # | 决策点 | 选项 | 建议 |
|---|---|---|---|
| **D1** | `document_chunks` 扩展方式 | A 全塞 `metadata JSONB`（零 schema 变更）／B 全加专用列／**C 混合** | **C**：高频过滤字段加列，其余塞 JSONB |
| **D2** | **embedding 由哪个字段算** | 旧：`content` 同源／新：**`embeddingText`**（含 Document/Section 前缀），`content` 列存纯净内容 | **`embeddingText`**（这是 section-aware 分块的核心收益，必须确认） |
| **D3** | 是否新增 `chunk_key`（= `chunkId`）+ 唯一索引 | 是（幂等 upsert/回溯）／否（塞 JSONB） | **是** |
| **D4** | 幂等策略 | `deleteByDocumentId` + 重插（沿用旧链路）／`chunk_key` upsert | **delete + 重插**（最小改动，已有实现） |
| **D5** | 入库方式 | 单条 insert（现状）／`<foreach>` 批量 | **批量**（598 chunks 单条会慢）；注意 pgvector 的 `CAST` 在批量里需逐值 |
| **D6** | Embedding 分批 | 一次性 `embedAll` ／分批（如 64）+ 重试 | **分批 + 重试**（598 条易触服务端限制） |
| **D7** | REFERENCE chunk（占比 29~52%） | 全量入库（检索时过滤）／入库时跳过 | **全量入库 + 标记 `chunk_type`**；检索过滤留到 QA 阶段用数据决定 |
| **D8** | **`documentId` 类型** | `AcademicChunk.documentId` 是 String；`documents.id` 是 BIGSERIAL | **生产链路传 `String.valueOf(documents.id)`**（会改变 `chunkId` 形态，需确认） |
| **D9** | 接入方式 | A 直接替换现有解析+分块两步／**B 平行入口 + 按类型分流** | **B**（先并存，验证后再统一） |
| **D10** | `valid=false` 的 canonical | 直接 failed／**仍入库 + 记 warning** | **仍入库**（warnings 是软问题，不丢内容） |
| **D11** | canonical JSON 是否持久化 | 存 MinIO（便于重跑分块、不重调 Marker）／不存 | **存 MinIO** |
| **D12** | Marker 不可用时降级 | 失败／回退到 LangChain4j pdfbox 抽取 | **失败并明确报错**（回退会产出"无章节结构"的假成功） |
| **D13** | 检索 QA 运行方式 | 依赖 pgvector／**内存 cos 相似度（离线）** | **内存离线版先做**（不依赖 DB/服务，可回归） |
| **D14** | gold set 来源与规模 | 人工出题／LLM 生成 | **人工出题**，每篇 10~20 题（5 篇共 50~100 题） |
| **D15** | QA 判定粒度 | ①chunk 命中 ②section 命中 ③页码命中 ④LLM 判分 | **①+③**（可自动、稳定） |

## 2. ① 把 `AcademicChunk` 接进 `document_chunks`

### 2.1 字段映射表（核心）

`AcademicChunk` 有 22 个字段，`document_chunks` 现有 11 列。

| AcademicChunk 字段 | 去向 | 备注 |
|---|---|---|
| `chunkId` | **新增列** `chunk_key TEXT` + 唯一索引 | 稳定可复现（`docId:scopeId:index`），适合幂等 |
| `documentId` | `document_id` | ⚠️ **D8：必须是 `documents.id`** |
| `chunkType` | **新增列** `chunk_type VARCHAR(16)` + 索引 | 供检索过滤/降权（REFERENCE 占比高） |
| `sectionId` | **新增列** `section_id VARCHAR(255)` + 索引 | 引用定位 |
| `sectionTitle` | **新增列** `section_title TEXT` | 展示 |
| `sectionPath` | **新增列** `section_path TEXT[]` + GIN 索引 | section-aware 过滤的关键 |
| `sectionLevel` | **新增列** `section_level INT` | level 过滤/重排 |
| `content` | `content` | 展示/引用（纯净内容） |
| `embeddingText` | **新增列** `embedding_text TEXT`（可空） | **D2：embedding 由它算出**；存一份便于重建/调试 |
| `blockTypes` | `metadata` | |
| `sourceBlockIds` | **新增列** `source_block_ids JSONB` | 溯源到 Marker 原始 block（定位原文） |
| `overlapBlockIds` | `metadata` | 默认关闭，通常为空 |
| `startPage` | `page_number` | 沿用现有列 |
| `endPage` | `metadata` | 或新增列 |
| `tokenCount` | `token_count` | |
| `charCount` | `metadata` | |
| `order` | `chunk_index` | 满足 `UNIQUE(document_id, chunk_index)` |
| `oversized` / `undersized` | `metadata` | 质量标签 |
| `contentHash` | **新增列** `content_hash VARCHAR(16)` | 变更检测 |
| `titleContext` | `metadata` | 与 `documents` 关联可查到，可选冗余 |
| `referenceIds` | `reference_ids JSONB` 或 `metadata` | 引用关系（可选） |
| —（旧链路）| `start_offset` / `end_offset` | **新链路留 NULL**（无字符偏移；不删列，避免破坏旧链路） |

### 2.2 schema 变更（方案 C）

```sql
ALTER TABLE document_chunks
  ADD COLUMN IF NOT EXISTS chunk_key        TEXT,
  ADD COLUMN IF NOT EXISTS chunk_type       VARCHAR(16),
  ADD COLUMN IF NOT EXISTS section_id       VARCHAR(255),
  ADD COLUMN IF NOT EXISTS section_title    TEXT,
  ADD COLUMN IF NOT EXISTS section_path     TEXT[],
  ADD COLUMN IF NOT EXISTS section_level    INT,
  ADD COLUMN IF NOT EXISTS embedding_text   TEXT,
  ADD COLUMN IF NOT EXISTS source_block_ids JSONB,
  ADD COLUMN IF NOT EXISTS content_hash     VARCHAR(16);

CREATE UNIQUE INDEX IF NOT EXISTS uk_document_chunks_chunk_key
  ON document_chunks (document_id, chunk_key);
CREATE INDEX IF NOT EXISTS idx_chunks_chunk_type   ON document_chunks (chunk_type);
CREATE INDEX IF NOT EXISTS idx_chunks_section_id   ON document_chunks (section_id);
CREATE INDEX IF NOT EXISTS idx_chunks_section_path ON document_chunks USING GIN (section_path);
```

> `init.sql` 是 `DROP TABLE ... CASCADE` 重建脚本 —— 改动需**同时**提供 migration 脚本或接受重建。

### 2.3 到 2.5（投递/限流/REFERENCE）

- **幂等**：沿用 `deleteByDocumentId` → 逐条/批量插入（D4）
- **批量**：新增 `insertChunksWithEmbedding(List<param>)`，用 `<foreach>`；pgvector 需逐值 `CAST(#{item.embedding} AS vector)`
- **分批 embed**：`embedAll` 按 64 条分批 + 失败重试（D6）
- **REFERENCE**：全部入库并打 `chunk_type='REFERENCE'`，其检索权重交由 QA 数据决定（D7）

### 2.6 验收
```text
□ 5 篇 canonical → 598 chunks 全部入库，无重复（UNIQUE 约束通过）
□ 抽查任意 chunk：content = AcademicChunk.content；embedding_text = embeddingText（带 Section: 前缀）
□ 同文档重复摄取两次 → chunk 数不翻倍（幂等）
□ section_path / chunk_type 可按 SQL 过滤
```

## 3. ② `CanonicalDocumentPipeline` 接入 ingestion

### 3.1 ⚠️ 最关键的冲突：`documentId` 类型

```text
AcademicChunk.documentId : String   （测试里是文件名，如 "Toward_robust_....json"）
documents.id             : BIGSERIAL (Long)
document_chunks.document_id : BIGINT REFERENCES documents(id)
```
`MarkerDocumentParser.parse(documentId, ...)` 的 javadoc 本就写着"系统现有 documents.id"，
但**测试链路传的是文件名**。

→ **D8 决策**：生产链路必须传 `String.valueOf(documents.id)`。
   否则 FK 约束失败；且 `chunkId`（= `documentId:scopeId:index`）的形态会随之一变。
   **若选文件名** → 需要给 `document_chunks.document_id` 加一个并行的 `chunk_key` 体系，复杂度上升。

### 3.2 接入方式（D9）

```text
方案 A：改 IngestionServiceImpl 两步
        DocumentParseService → CanonicalDocumentPipeline
        TextSplitterService  → SectionAwareChunker
方案 B（推荐）：新增平行入口 + 按类型分流
        .pdf  → 学术链路（Marker→…→Chunker）
        .txt/.md/其它 → 旧链路（LangChain4j）
```
B 的好处：旧链路零回归；可逐篇灰度。

### 3.3 分流条件
`DocumentParserFactory` 现按扩展名选 parser → 分流同样按扩展名（或 mime，`documents.file_ext` 已有列）。
**D-附加**：是否允许显式覆盖（上传参数强制走某条链路）？

### 3.4 Marker 依赖与降级（D12）
- Marker 经 SSH Tunnel（`127.0.0.1:18001`），`read-timeout: 900s`
- 不可用时：**失败并明确报错**（回退 pdfbox 会产出"无章节结构"的假成功，污染向量库）
- `MarkerClient` 已有 5 类异常 → 映射到 `documents.status='failed'` + `error_message`

### 3.5 状态机与 `valid=false`（D10）
现有状态可复用：`uploaded → parsing → chunking → embedding → indexed | failed`
- `validation.valid()==false` → **仍入库**，warning 写 `ingestion_tasks.error_message`? 或新增 `metadata`
- 是否需要在 `parsing` 下细分"marker 调用 / repair / clean"子步骤？（`ingestion_tasks.current_step` 已有列）

### 3.6 产物持久化与图片（D11）
- canonical JSON → MinIO（`stored_file_name` 旁挂 `canonical.json`）：便于**只重跑分块**而不重调 Marker（我们已有 `rawJsonDir_cleanOnly_savesOutput` 这类离线能力）
- 图片：`FigureImageStorage` 需切到 `MinioFigureImageStorage`（生产）；`LocalFigureImageStorage` 仅测试

### 3.7 验收
```text
□ 上传 1 篇 PDF → documents.status 最终 indexed，chunk_count = 该篇 chunk 数
□ document_chunks.document_id 与 documents.id 一致（FK 通过）
□ Marker 不可用时 → failed + 可读 error_message（不静默降级）
□ 同一 PDF 重复上传 → 不产生重复 chunk
□ 旧链路（txt/md）零回归
```

## 4. ③ 检索 QA 基线

### 4.1 关键洞察：**可以完全离线做**（D13）

```text
把 5 篇的 598 个 chunk 的 embedding 预先算好（缓存到本地文件）
→ 在内存里算 cos 相似度 → 出 recall@k / MRR
→ 【不需要 pgvector、不需要 DB、不需要 LLM】
```
用于"**分块策略对比**"完全足够（差异只在向量检索的近似性；`ivfflat` 近似的影响可后续单独测）。
好处：可作为**可回归的测试**（像现有 `RealPaperQaTest` 一样带 `Assumptions` 跳过）。

### 4.2 gold set（D14）
- 来源：**人工**从 5 篇 canonical 出题（避免 LLM 自证）
- 规模：每篇 10~20 题 → 共 50~100 题
- 每题记录：
```text
question
expected_section_path（可空 = 跨章节问题）
expected_source_block_ids（至少一个）
expected_page（用于页码级判定）
question_type（事实/数值/方法/对比/图表）
```
- 覆盖：TEXT / TABLE / FIGURE / LIST 各若干；**必须包含表格数值题**（验证表格切分质量）

### 4.3 指标（D15）
```text
recall@1 / recall@3 / recall@5 / recall@10
MRR（首个命中排名倒数）
precision@5
no-answer 拒绝率（问全集外的问题 → 期望 minScore 过滤掉）
引用准确率（返回的 source page 是否正确）
分类别：TEXT / TABLE / FIGURE / REFERENCE 各自的召回率
```

### 4.4 对照组（回答"section-aware 到底比字符切分好多少"）
```text
A（旧）：TextSplitterService 800/120 字符递归   ← 已有实现
B（新）：SectionAwareChunker（598 chunks）      ← 已建
同 gold set、同 embedding 模型、同 topK
```
> B 还应有**消融**：embedding 用 `content` vs `embeddingText`（验证 Section 前缀的价值 → 直接回答 B/C 类的收益）

### 4.5 生成质量（二阶段，需 LLM）
- 引用正确性（答案是否真出自所引 chunk）、无幻觉率、拒答合理性
- 复用现有 `ChatServiceImpl` 全链路（可加一个 `retrievalQa` 测试入口）

### 4.6 验收
```text
□ A/B 对照表（recall@k / MRR / 分类别召回）
□ content vs embeddingText 消融表
□ 结论：section-aware 是否有收益、收益在哪一类
□ 用该数据决定：REFERENCE 是否检索过滤、overlap 是否开启、targetTokens 是否需标定
```

## 5. 建议顺序

```text
Phase 0（前置验证，必须先做，不写业务代码）
  □ Ollama bge-m3 /v1/embeddings 可用 + 维度 1024（smoke）
  □ docker compose up -d（pgvector）+ 应用 init.sql / migration
  □ 确认两条 embedding 调用路径（OpenAiClient vs LangChain4j EmbeddingModel）结果一致
  □ 修正 README（1536/text-embedding-3-small → 1024/bge-m3）

Phase 1（① 入库）— 依赖 Phase 0
  □ migration 脚本（新增 9 列 + 3 索引）
  □ AcademicChunk → DocumentChunkInsertParam 映射器（含 embeddingText→embedding）
  □ 批量 insert + 分批 embed + 重试
  □ 幂等验证

Phase 2（② 接入 ingestion）— 依赖 Phase 1
  □ documentId ← documents.id
  □ 分流（PDF → 学术链路；其余 → 旧链路）
  □ canonical JSON 存 MinIO + 图片切 MinioFigureImageStorage
  □ Marker 异常 → failed
  □ 旧链路零回归

Phase 3（③ 检索 QA）— 可与 Phase 1/2 并行（离线内存版即可先跑）
  □ 人工 gold set（50~100 题）
  □ 离线 embedding 缓存 + 内存 cos 检索
  □ A/B 对照 + content/embeddingText 消融
  □ 出报告 → 决定 REFERENCE 过滤 / overlap / targetTokens
```

## 6. 风险与前置

| 风险 | 说明 | 对策 |
|---|---|---|
| **D8 `documentId` 语义变更** | 从文件名改为 `documents.id` 会改变 `chunkId` 形态，可能影响已有测试/产物 | 改前先确认；测试链路可继续用文件名（保持离线 QA 不变） |
| **embedding 依赖外部服务** | Ollama bge-m3 未验证；无 smoke | Phase 0 先验证；QA 用 `Assumptions` 跳过以不阻塞 CI |
| **单条 insert 性能** | 598 chunks × 单条 + 单次 embedAll | 批量 + 分批（D5/D6） |
| **pgvector 维度锁死** | `VECTOR(1024)` 与 bge-m3 维度绑定；换模型需改表 | 变更前确认模型；README 同步 |
| **`ivfflat lists=100` 偏大** | 小数据量下召回可能劣于精确检索 | 有数据后实测；必要时先不加 ivfflat 索引 |
| **Marker 强依赖** | SSH Tunnel + 900s 超时 | 明确失败语义（不回退）；必要时给 ingestion_tasks 细分步骤 |
| **检索层无测试** | ChatService/检索/mapper 零覆盖 | Phase 3 顺带补上最小回归 |
